## F24 Gradle locking and advisories, November 6

Branch `claude/next-remedy-tranche-13` stacks on `claude/next-remedy-tranche-12` (draft #93, F13 screens), which stacks on #92 (F19), #91 (F24 launch runs) and #90 (F13 view models), so the PR targets tranche 12's branch and should merge after #93, #92, #91 and #90. It closes the Gradle half of F24's advisory scanning that tranche 10 left open.

Locking. `apps/android` now uses strict Gradle dependency locking, with `app/gradle.lockfile` for the app classpaths (Robolectric, `ui-test-junit4`, `kotlinx-coroutines-test` and `lifecycle-runtime-compose` included) and `buildscript-gradle.lockfile` for plugins; scope and procedure are in [Updating Gradle locks](release-checks.md#updating-gradle-locks). A build fails when a locked classpath resolves a module the lock doesn't list, and when a declared version is raised past the locked one; a declared version below the locked one is overridden by the lock, not rejected. Locking all configurations was tried first and rejected: it puts lint, the Kotlin compiler and the test-device runner (netty, bouncycastle and other build-machine libraries) in the lockfile, which made the scan report dozens of advisories in tools that never ship. A Dependabot Gradle pull request needs the regeneration run on its branch.

One workaround is in the build. AGP aligns `debugAndroidTestRuntimeClasspath` with the app's runtime versions, and Gradle doesn't write a module reached only through that alignment (`kotlin-stdlib-common`) to the lock, so strict mode rejected the build. `app/build.gradle.kts` declares it as `androidTestRuntimeOnly`, with a comment on what to do if another module shows up. Lenient locking would avoid this but lets a newly added dependency go unlocked and unscanned.

The wrapper. `distributionSha256Sum` is set in `gradle-wrapper.properties` (the value matches the checksum Gradle publishes for 8.11.1), and both Android jobs run `gradle/actions/wrapper-validation`, pinned to the v6.4.1 commit, before they run `./gradlew`. Gradle and AGP versions are unchanged.

Scanning. `gradle-advisories` in the Dependency advisories workflow runs the same checksum-verified osv-scanner v2.7.0 as `swiftpm-advisories`, on every pull request, push to `main`, weekly and on demand. It fails on any known advisory in `app/gradle.lockfile`. It lists the plugin lockfile's advisories in the job summary without failing, as `npm-advisories` does for development dependencies: on November 6 that file had 54 advisories in 14 packages (AGP's netty, bouncycastle, guava, commons-compress and the Kotlin Gradle plugin), all on the build machine and fixable only by raising AGP or Kotlin, which this tranche doesn't do. `.github/dependabot.yml` has a note on the lock step.

Advisories found in the app lockfile, all fixed. The first scan found 9 (2 critical, 4 high): `guava` 31.1-jre in the shipped app (GHSA-xxph-c9ww-hj94 deserialization memory use, and two smaller ones), through `google-api-client` 2.0.0 from the calendar client, and `bcprov-jdk18on` 1.78.1 in the unit-test classpath only, through Robolectric. A `constraints` block in `app/build.gradle.kts` raises guava to 33.7.2-jre and bcprov to 1.85. bcprov 1.85's jar holds Java 25 class files that Jetifier can't read, so `gradle.properties` tells Jetifier to skip `bcprov-jdk18on`. The guava bump changes a library the Google Calendar client uses at runtime; no test exercises that client against a real response, so before release, run calendar sync on a device against a real Google account.

Not run locally: the wrapper validation action, `gradle-advisories` (needs the CI download path), and `connectedDebugAndroidTest`, which resolves the test-device runner's configurations under strict locking; CI covers those.

## F13 remaining Android screens, November 6

Branch `claude/next-remedy-tranche-12` stacks on `claude/next-remedy-tranche-11` (draft #92, F19), which stacks on `claude/next-remedy-tranche-10` (draft #91, F24) and `claude/next-remedy-tranche-9` (draft #90, F13 view models), so the PR targets tranche 11's branch and should merge after #92, #91 and #90. It finishes F13 step 2 for the Android screens tranche 9 left on `rememberCoroutineScope`.

What moved. Each screen now has a model held by tranche 9's `ScreenModelViewModel`: `PollListModel` (join-by-code sheet, pull-to-refresh, load more, retry), `TimeOptionResponsesModel`, `SettingsModel` (sign out, restore purchases, calendar toggles), `ProfileEditModel` (form fields and save), `PaywallModel` (plans, selection, purchase, restore) and `SignInModel` (email field, magic link, browser sign-in, Google sign-in). The poll list data itself stays in `PollService`, which is process-lifetime and already resets on an account change; the list model owns only the screen's commands and sheet state. One generic `ScreenModelFactory` and a holder function per screen in `ui/ScreenViewModels.kt` replace what would have been six more dedicated factories; the two tranche 9 factories are unchanged. Models reach services through narrow interfaces (`PollListPolls`, `PollResponsesPolls`, and in the new `services/AccountScreenDependencies.kt` `AccountScreenAuth`, `SignInAuth`, `ScreenBilling` and `SettingsCalendar`), which `PollService`, `AuthService`, `CalendarService` and `PurchaseService` implement. `PurchaseService.purchase` and `restorePurchases` now return `Unit` to fit `ScreenBilling`; no caller used the returned `CustomerInfo`. `ScreenModelFactory` takes `open` and `start` lambdas that close over the services; neither it nor the models hold an Activity, `Context` or `LifecycleOwner`. The two calls that need an Activity take it as an argument for that call only: `PaywallModel.purchase(activity)` and the `GoogleCredentialSource` the sign-in screen builds from its Activity.

F12 contract. Every model captures its account (the poll account key, or the auth account id plus identity generation) when it is made and checks it before it publishes a result, so a late result after an account change is dropped. The holders live in navigation-entry stores nested in the session store, so a new identity generation clears them and cancels their work.

Scope decisions.
- Sign-in is outside the authenticated tree. `ContentView` now composes it in `SessionScope` for the current identity generation as well. The generation changes when a session is accepted or ended (sign-in, sign-out, expiry), not when an attempt begins, so the sign-in model lives for the whole attempt and ends when the session changes; signing out gives a fresh form. The Google credential UI belongs to the Activity, so `AuthView` cancels that one job when its composition is disposed (a rotation during the credential prompt asks the person to tap again, as before). Magic-link and browser sign-in run in `viewModelScope` and survive rotation, and the email field and error text are kept.
- Paywall and settings sit inside `SessionScope` already. Paywall closes through a `finished` flag on the model, as creation does with `created`, so a purchase that completes during recreation still closes the screen.
- Refresh on re-entry: the poll list used to reload every time its composable entered composition. It now reloads when it resumes after being disposed, which covers a child screen, a tab switch and an Activity recreation (so a rotation still reloads the list). It uses `RefreshOnReturn`, with `coverWithChild()` called from `onDispose`. The responses screen had no child and loads once when it is made; Retry reloads. Settings, profile and paywall loaded nothing on re-entry beyond the paywall's offerings, which load when the holder is made.
- Behavior change in `MainTabView`: the two tab `NavController`s are hoisted above the tab switch. Before, leaving a tab disposed its controller while its entries' stores stayed in the shared nav store until the session ended, so the models of an abandoned entry were never cancelled. Now each tab keeps its back stack when you switch tabs and returns to the screen you left. This is the one user-visible difference.

State exposure. The screens keep Compose snapshot state, as in tranche 9, and do not use `collectAsStateWithLifecycle`. The state they read (`AuthService`, `PollService`, `CalendarService`, `PurchaseService`) is `mutableStateOf`; the auth `sessionStatus` flow is collected inside `AuthService` in the application scope and is not a screen-facing source, so no `Flow` reaches a composable.

Tests. `RemainingScreenModelsTest` (43 tests) covers each new model's success path and, where the model has one, its failure reporting. Every model also has a test that a result arriving after an account change is dropped and one that clearing the holder's store cancels its work. Replaced loads and attempts are tested for the responses and sign-in models. `NavigationScopingTest` gained 5 tests that host the real `PollListView` and `TimeOptionResponsesView` in the session and navigation chain: the list loads once and reloads on return from a child, keeps its join sheet across a child screen, and is cancelled by a new identity generation; a pushed responses screen loads once, is cancelled when popped (and gets a fresh model when reopened), and is cancelled by a new generation. `ScreenViewModelTest`'s factory guard now includes `ScreenModelFactory`. `ScreenModelRecreationTest` (androidTest) is unchanged: it builds its own holder and still describes the store behavior.

Local results (portable Temurin 21 and Android SDK 36 in a temp directory, no emulator): `./gradlew :app:testDebugUnitTest :app:assembleDebugAndroidTest` passed; `:app:testDebugUnitTest` ran **201 tests**, 0 failures (153 before, plus 43 and 5). `assembleDebug` also built. No emulator ran locally, so Activity recreation of the new screens, the Google credential prompt and a purchase were not exercised on a device. No test covers the sign-in screen's `SessionScope` in `ContentView` or the `MainTabView` change that keeps each tab's back stack (`NavigationScopingTest` hosts `PollListView` and `TimeOptionResponsesView` only); both are open until a device check.

Reviews. Independent correctness, structure and simplification reviewers ran on the code. Correctness found no defects. Fixed from the structure and simplification reviews: the shared holder key for the account screens, the unused `polls` exposure on `PollListModel`, an unused import, the purchase parameter alias, the refresh-contract KDoc and the factory guard test. Deferred: folding the two tranche 9 factories into `ScreenModelFactory` (they are referenced by tranche 9 tests), the dead `Settings` and `ProfileEdit` routes in `PollNavHost` and the second hand-written settings graph in `MainTabView` (both pre-existing), moving `sameAccount` next to the interfaces, sharing the test fakes between `RemainingScreenModelsTest` and `NavigationScopingTest`, and narrowing `PollDetailView` and `CreatePollView` to interfaces.

## F13 Android view models, November 5

`ScreenModelViewModel` now holds each model. `PollDetailViewModelFactory` and `PollCreationViewModelFactory` build it from the services, clock and draft-store factory the screen already receives from `AppContainer`; they hold no Activity, `Context` or `LifecycleOwner`. The detail load starts when the holder is made, and again when the entry resumes after a child screen (the responses list) covered it; a rotation does not reload. F12 contract: a model is bound to the account key it was made under and drops late results, as before. In addition, `SessionViewModelStores`, an Activity-scoped `ViewModel` created in `ContentView`, provides the authenticated tree a `ViewModelStore` for each identity generation (the key `ContentView` already used to recreate the tree). Moving the state to `StateFlow` would rewrite every field of both models and their tests, and nothing in this step needs it. No `onCleared` override was needed on the screen holders, since `viewModelScope` ends with them; `SessionViewModelStores.onCleared` clears every session store. ## F23 web result checks, November 4

Branch `claude/next-remedy-tranche-4` started from fetched main `46b98ae`, which contains merged #83. It takes the web item the section below left open: the `json` function results the web cast to its row types after checking only some of their fields.

`apps/web/src/lib/rpc-results.ts` checks each `json` result the polls store uses before the store publishes it: the poll list pages, poll detail, guest detail, response pages, creation, both joins, finalization, and loading and saving availability. Each check names every key of its type, optional keys included, and each poll, time option, participant and response row check names every generated column with its type. After a migration adds or removes one of those columns, or changes its generated type, and the types are regenerated, svelte-check fails until the check matches. A retype that keeps the TypeScript type, such as `int4` to `int8`, doesn't. In scratch edits, leaving out a column or an optional key, checking a nullable column as non-null, checking a number column as a string, checking an optional key as required, adding a column the table doesn't have, and leaving a member out of the `poll_status` list or adding one it lacks each failed svelte-check. Keys a result has beyond its type are ignored. Timestamps must have the ISO 8601 form Postgres writes, including years past 9999 and a trailing ` BC`, or end in `Z`. The check matches a pattern rather than calling `Date.parse`, because browsers disagree about fractions finer than milliseconds. `checkedPage` now takes a check for its items.

Results that used to pass now fail in these cases. A poll list, detail or response page with any malformed row is an incomplete read, as a missing poll id already was. A creation result with any malformed field reports that creation could not be confirmed, and the draft keeps its operation for retry. A finalization or member join whose result fails its check now throws "could not be confirmed"; before, the result was published unchecked. Both commands can be retried safely. A guest join already reported "could not be confirmed" for a bad token or poll id; it now also does for a malformed participant row, and the kept token makes the retry safe. A loaded or saved availability snapshot with a malformed response now fails its check and isn't applied. A guest detail that fails its check, or that names another participant, is now an incomplete read and keeps the guest's capability. Before, a detail without a poll dropped the capability; a null detail or another poll's detail still does.

Because the checks require every column, dropping or renaming a column of those four tables, or retyping one to a different JSON type, breaks web reads, and makes creation, joins and finalization report "could not be confirmed" after the server commits them, from the moment the migration is applied until the web is redeployed. Adding a column doesn't break the deployed web, because extra keys are ignored, but a web built from the regenerated types fails against a database without the column, so apply such a migration before deploying the web. The check can't stop requiring a column until the regenerated types drop it, so deploy the web right after a migration that drops, renames or retypes one; the gap between the two is the failure window. Nothing in the repository deploys them together; it is an owner step. Creation replays return the result stored with the original request. No migration has added a column to `polls` or `poll_time_options` since `create_poll` started storing results, so each stored result should have every column the checks require; stored results in a hosted database weren't read. A migration that adds a column to either table must also update the stored results in `private.poll_creation_requests`, or a replay of an older request will fail its check.

A worker must request a reservation from the coordinator, and wait for explicit approval, before it queries or uses a simulator or emulator, starts a local server, or connects to an existing local service. The request names the device ID or bind address/port, the purpose, the expected duration, and any install, reset, or stop actions. Approval covers only the named resource and actions. Workers report when they release it; elapsed time does not grant access. Occupied or user-owned resources must not be stopped or reset without permission.

These need no reservation: static checks, pure compilation (including `xcodebuild` against a generic destination, with no simulator device), local Gradle builds with `--no-daemon` and no emulator or adb, and isolated in-process PGlite or offline Deno tests that open no listening port.

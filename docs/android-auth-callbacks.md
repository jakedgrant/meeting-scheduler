# Android authentication callbacks

Android uses `meetingscheduler://auth/callback?attempt=<uuid>` for Supabase authentication. `MainActivity.onCreate` and `onNewIntent` send this exact route to the same application-owned router. The calendar route remains `meetingscheduler://calendar/callback`; it only requests current-account connection metadata from the calendar backend.

## SDK and request configuration

The app pins Supabase Kotlin **3.3.0**. Auth configuration sets `scheme = "meetingscheduler"`, `host = "auth"`, `defaultRedirectUrl = "meetingscheduler://auth/callback"`, and `FlowType.PKCE`. OTP requests and the Google browser fallback append the originating attempt UUID to that base route and pass the resulting explicit redirect. Native Credential Manager Google sign-in retains its ID token and original nonce.

Current official [initialization](https://supabase.com/docs/reference/kotlin/initializing), [code exchange](https://supabase.com/docs/reference/kotlin/auth-exchangecodeforsession), and [native mobile deep-link](https://supabase.com/docs/guides/auth/native-mobile-deep-linking) documentation were checked against the installed 3.3.0 Android artifact. The pinned SDK exposes `awaitInitialization`, `exchangeCodeForSession(code, saveSession = false)`, `importSession`, and the ID-token provider's custom success callback. Tests execute those SDK methods through Ktor MockEngine.

The router accepts the exact scheme, host and `/callback` path. It rejects other paths, credentials in the authority, ports and malformed URIs. The originating UUID must appear exactly once in the query and match the persisted attempt before SDK exchange, error reporting or pending-state mutation. Missing, malformed, duplicate or obsolete UUIDs are ignored. Provider errors can arrive in the query or an error-only fragment; implicit credential fragments are rejected. It rejects missing/duplicate codes and reports provider cancellation or exchange failure without logging credentials. PKCE verifier validation and one-time code handling belong to the SDK/server. The client never imports URL-supplied access tokens.

## Attempt ownership and process startup

A pending attempt is stored before starting OTP/browser work. It contains an account/server-session/generation key, process identifier, attempt UUID, creation time and readiness flag. Starting another attempt replaces the UUID. The UUID travels in the requested redirect and incoming URI; a late A link cannot borrow the marker from a newer B or signed-out attempt. Native Google invalidates pending browser/OTP attempts before Credential Manager opens, and passes its captured revision through both native UI paths. SDK initiation and code exchange share a mutex so an older successful exchange cannot delete a newer request's PKCE verifier. Queued obsolete work rechecks its owner before entering the SDK.

An account boundary invalidates the persisted attempt. A valid old code arriving only after B signs in is rejected before exchange. An older exchange's success, failure or cleanup cannot affect a newer attempt in the same session. Explicit sign-out invalidates attempts even when already signed out. Service disposal invalidates caller-owned native work as well as owned callback tasks; delayed native success or failure cannot import afterward. Authentication links received before SDK initialization wait for restoration. Only the initial restoration in a new process may rebind a saved attempt, and only when its owner matches both the restored account and server session lineage. A refreshed JWT from that same server session can restore the attempt; a new login for the same UUID cannot. A signed-out attempt cannot replace a restored B session. Attempts expire after 15 minutes. Duplicate delivery is ignored; consumed attempts remain consumed across process restart.

Callbacks queued while a request is still starting wait for that request to become ready or obsolete. A cold process can recover a saved pending attempt after the original HTTP response was lost, using the persisted SDK verifier. A link opened on another app installation has no matching attempt/verifier and must be requested again there.

## Session publication and sign-out

SDK refresh jobs and gateway credential mutations run on `Dispatchers.Main.immediate`. `AtomicSessionManager` uses the same default Settings backing, scoped key and public `UserSession` serializer as 3.3.0, including its legacy `session` key migration. The Android backing uses `SharedPreferences.apply`. Save/remove update memory synchronously, so there is no dispatcher switch between persistence and SDK auth-state publication. This replaces the pinned default manager's `withContext(IO)` gap without changing the saved schema.

Local session identity combines the user ID with the JWT's `session_id`, which Supabase [documents as the server session identifier](https://supabase.com/docs/guides/auth/sessions#access-token-jwt-claims). An ordinary token refresh in that lineage retains the generation; a fresh session for the same user advances it and resets old work. Missing/malformed claim data uses a hash of the exact credential as a conservative fallback. Persisted callback ownership includes this lineage. The hash keeps raw credentials out of the pending-attempt record. This key partitions client state; backend authorization remains authoritative.

Gateway imports serialize, check ownership after entering the mutation boundary, cancel old refresh work and publish the new session before starting its refresh worker. Poll RPCs, direct poll/detail/participant/response reads, status updates, profile loads/updates and calendar requests bind the originating app-session credential explicitly; a later SDK credential lookup cannot dispatch an old envelope as B. Direct PostgREST select/update builders in 3.3.0 append custom headers to the default Authorization. Those paths use a request-owned SDK view with a captured `accessToken` provider and the existing PostgREST configuration/serializer/HTTP transport. The view registers no plugin, creates no network client and owns no listeners. Its pinned internal SDK boundary is covered by transport tests asserting exactly one header. Calendar conflict work captures ownership before device-calendar suspension and checks it again before backend dispatch. Transport tests assert every Authorization header value, including the absence of duplicate A/B headers. Actual SDK transport tests delay old refresh success and failure across replacement and returning-account sessions. They check both SDK credentials and persisted credentials.

Explicit sign-out captures the original session before resetting visible state or suspending. Application-owned cleanup survives disposal of the settings screen. The bounded local mutation cancels refresh and removes shared credentials only if account plus server-session lineage still match the captured original; it removes an ordinary refresh from that lineage, while leaving B or a fresh A session intact. That bounded removal survives cancellation, while remote I/O remains cancellable. Further status events from the explicitly signed-out lineage cannot resurrect its UI state. Remote revocation uses an ephemeral in-memory SDK client containing only the captured original, with `SignOutScope.LOCAL`, even when another session was installed while cleanup was queued. Delayed success/failure cannot clear or revoke the replacement. The local scope revokes the captured session rather than signing out other devices or a new reauthentication session.

## Required external configuration

These are owner actions. Hosted configuration and real provider sign-in were not verified in this workstream.

1. Add the exact allowlist glob `meetingscheduler://auth/callback\?attempt=*` to the intended Supabase project's Auth redirect list. The backslash belongs in the allowlist pattern; actual redirects are `meetingscheduler://auth/callback?attempt=<uuid>`. Supabase's [documented glob rules](https://supabase.com/docs/guides/auth/redirect-urls#use-wildcards-in-redirect-urls) treat `?` as a wildcard, `\?` as a literal question mark and `*` as non-separator characters. Keep calendar redirects configured separately according to [calendar credentials](calendar-credentials.md).
2. Enable the intended Google OAuth provider and register the project's Supabase Auth callback URL (`https://<project-ref>.supabase.co/auth/v1/callback`) in its Google web OAuth client. Confirm the configured web client ID matches the native ID-token audience.
3. Register the intended Android application IDs and signing certificate SHA-1 values for native Google. Debug and release signing differ; use the actual intended certificates described in [Android release signing](android-release-signing.md).
4. Keep the OTP email link template compatible with Supabase's confirmation URL and requested redirect. Verify the complete `attempt` query survives OTP confirmation and browser Google redirects, including provider cancellation/error URLs, on the installation that requested it. Query preservation and hosted glob acceptance require an approved provider test; local SDK transport tests establish only the requested URI. Links without the originating UUID are ignored and require a new sign-in request.
5. Use an approved test project/account to verify native Google, browser Google and OTP with the app cold and warm; cancellation, expiry and replay; A → B and A → logout → A; offline sign-out and reconnection. Confirm RevenueCat's actual current app user ID in the test dashboard. Local tests do not establish hosted allowlists, email delivery, Google consent, RevenueCat identity or purchases.

The emulator checks used a fresh task-owned Android 36 device with Wi-Fi and mobile data disabled before app installation. They exercised Activity routing, recreation and a persisted cold-start cancellation callback. No real account or provider session was used. Exact commands and results are recorded in the [Android workstream evidence](architecture-remediation-evidence-2026-10-23/f12-f14-f22/android.md).
